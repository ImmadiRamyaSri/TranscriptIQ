# TranscriptIQ 🤖

**European Robotic Surgery Market Intelligence — Multi-Call Transcript Analyzer**

TranscriptIQ is a Retrieval-Augmented Generation (RAG) application designed to analyze expert interviews about the European robotic surgery market.

It processes timestamped interview transcripts, retrieves relevant expert responses, and generates evidence-grounded answers with citations. It also supports individual expert analysis and cross-expert comparison.

The current dataset contains three expert interviews from **France, Germany, and the United Kingdom**.

## Features

- **Transcript Viewer:** Explore parsed transcripts, speaker turns, and timestamps.
- **Interview Guide:** Retrieve answers to standardized interview questions separately for each expert.
- **Cross-Transcript Analysis:** Compare expert perspectives, identify common themes, and highlight differences.
- **Ask Questions:** Ask free-form questions across all indexed transcripts through a conversational interface.
- **Expert-Level Retrieval:** Filter retrieval to a selected expert when analyzing interview guide questions.
- **Semantic Retrieval:** Retrieve relevant transcript chunks using sentence embeddings and FAISS.
- **CrossEncoder Reranking:** Rerank the retrieved candidates to prioritize the most relevant evidence.
- **Evidence Sufficiency Verification:** Check whether the selected transcript evidence actually supports the question before generating an answer.
- **Grounded Citations:** Include expert name, market, and timestamp references in answers.
- **Unsupported Question Handling:** Return `Information not found in the transcripts.` when the available evidence is insufficient.

## Getting Started

### 1. Clone the repository

```bash
git clone https://github.com/ImmadiRamyaSri/TranscriptIQ.git
cd TranscriptIQ
```

### 2. Create a virtual environment

```bash
python -m venv .venv
```

Activate it:

**Windows PowerShell**

```powershell
.venv\Scripts\Activate.ps1
```

**macOS / Linux**

```bash
source .venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

### 4. Configure the Groq API key

Create a `.env` file in the project root directory:

```env
GROQ_API_KEY=your_groq_api_key
```

Replace the placeholder with your own Groq API key.

**Important:** Never commit your `.env` file or expose your API key on GitHub. Commit only the redacted `.env.example` file.

### 5. Check the data files

Place the three interview transcripts in:

```text
data/transcripts/
```

Place the interview guide at:

```text
data/Interview_Guide.txt
```

The transcript parser expects expert information such as name, role, and market, followed by timestamped speaker turns.

The current chunking implementation pairs interviewer questions with the corresponding expert responses.

### 6. Run the application

```bash
streamlit run app.py
```

Once the application opens, click **Ingest & Index Transcripts** in the sidebar to parse the transcripts and build the FAISS vector store.

You can then explore the four application tabs.

## How It Works

### 1. Transcript Parsing

`transcript_parser.py` processes the interview transcripts and extracts:

- Expert name
- Professional role
- Market
- Timestamped speaker segments

It also parses standardized questions from the interview guide.

### 2. Question-Answer Chunking

`chunker.py` groups each interviewer question with the corresponding expert response.

Each chunk retains metadata such as:

- Expert name
- Role
- Market
- Timestamp

This preserves the interview context and enables source traceability.

### 3. Embedding and Vector Indexing

`vector_store.py` converts transcript chunks into LangChain documents.

The embedding model `all-MiniLM-L6-v2` generates vector representations, which are indexed using FAISS.

The vector store also supports expert-specific retrieval.

### 4. Retrieval and Reranking

For a user question, the RAG pipeline:

1. Retrieves up to 20 candidate transcript chunks from FAISS.
2. Uses a CrossEncoder to score and rerank the retrieved chunks.
3. Selects the top 5 chunks for further processing.

This two-stage retrieval approach improves the relevance of the evidence passed to the language model.

### 5. Evidence Sufficiency Verification

Before generating an answer, the application checks whether the retrieved evidence sufficiently supports the user's question.

The evidence checker evaluates the relationship between the question and the retrieved transcript content.

Semantic similarity alone is not treated as proof that the transcripts contain the answer.

If the evidence is judged insufficient, the application returns:

```text
Information not found in the transcripts.
```

No supporting sources are displayed for these unsupported answers.

This is an LLM-based verification step and is not a formal guarantee against every incorrect judgment.

### 6. Grounded Answer Generation

When sufficient evidence is available, the language model generates an answer using the selected transcript chunks.

Answers include source references in the following format:

```text
[Expert Name, Market, Timestamp: MM:SS]
```

This allows users to trace generated answers back to the original interviews.

### 7. Conversational Question Answering

The Ask Questions tab supports conversational interactions.

The chat workflow uses conversation history to provide context for follow-up questions, while retrieving and checking transcript evidence before generating answers.

Conversation history is maintained within the current Streamlit session.

### 8. Cross-Expert Analysis

`cross_analysis.py` retrieves relevant answers for individual experts and combines the original transcript evidence.

The language model then synthesizes the evidence to identify:

- Common themes across experts
- Differences in expert perspectives
- Market-specific observations
- Areas where experts provide different viewpoints

The analysis is grounded in the supplied interview transcripts.

## Evaluation

The project includes an evaluation dataset containing **26 questions** designed to test evidence sufficiency.

The evaluation categories are:

| Category | Number of Questions |
|---|---:|
| Supported / Relevant Questions | 6 |
| Unrelated Negative Questions | 15 |
| Semantically Similar but Unsupported Questions | 5 |
| **Total** | **26** |

The hard-negative questions are particularly important because they test whether the system can distinguish genuine supporting evidence from content that is merely semantically similar.

Run the evaluation using:

```bash
python evaluate_retrieval.py
```

The evaluation workflow:

1. Loads and parses the three transcripts.
2. Creates the transcript chunks.
3. Builds the FAISS vector store.
4. Retrieves up to 20 candidate chunks per question.
5. Reranks the candidates and selects the top 5.
6. Runs the evidence sufficiency check.
7. Compares the predicted evidence status against the expected label.
8. Reports the evaluation results and writes them to a CSV file.

The evaluation dataset is small and specific to the current transcripts. Its results should not be interpreted as a general performance guarantee.

## Smoke Testing

Run the RAG smoke tests using:

```bash
python test_rag.py
```

The test script checks examples of:

- A supported question about factors influencing robotic surgery adoption.
- An unsupported question about robotic surgery adoption in the United States.
- An unsupported question about the average purchase price of a robotic surgery system in India.

The expected behavior for unsupported questions is the insufficient-evidence fallback rather than an unsupported generated answer.

## Current Limitations

- The current dataset contains only three expert interviews and 21 transcript chunks.
- The chunking logic is designed around the current interviewer-question and expert-response structure.
- The evaluation dataset contains only 26 questions.
- Evidence sufficiency is determined by an LLM and can produce false positives or false negatives.
- FAISS runs in memory and the index is rebuilt when transcripts are ingested.
- Chat history is maintained within the current Streamlit session and is not persistent across sessions.
- Answers are grounded in the supplied transcripts and are not independently verified against external sources.
